# grasp-skill-create

grasp-* プレフィックスの Skill（システム理解・把握系）を作成・編集するためのルール集。

## いつ作るか

以下を「把握したい」ときに作る：
- モジュール・レイヤーの責務と境界
- 設計上のトレードオフや意思決定の経緯
- ファイルをまたぐ依存関係やデータの流れ

**対象外**：コード生成・コマンド実行・テスト実行など、生成・実行系は別プレフィックスを使う。

## 命名規則

| プレフィックス | 用途 |
|--------------|------|
| `grasp-` | 理解・把握系（このルールの対象） |
| `run-` | 実行系（devサーバー起動など） |
| `gen-` | 生成系（コード・ファイル生成など） |

例：`grasp-auth`、`grasp-shift-schedule`、`grasp-db-layer`

## 記述方針

**書くこと**
- 設計方針・責務・レイヤーの役割
- トレードオフと選択の理由
- 意思決定の経緯（「なぜこうなっているか」）
- 注意点・落とし穴・暗黙のルール

**書かないこと**
- 関数名・行番号・コード断片（コードを読めば分かる）
- ファイル一覧（`find` や `ls` で分かる）
- 「何をしているか」の説明（コード自体が語る）

> コードは「何をするか」を語る。Skill は「なぜそうなっているか」を語る。

## テンプレート

```markdown
# grasp-<対象名>

<対象の一言説明>

## 全体像

<このモジュール/レイヤーが存在する理由と全体の中での位置づけ>

## 責務の分担

<誰が何を担うか。境界はどこか>

## 依存方向

<何に依存し、何から依存されるか。循環がないか>

## 重要な設計判断

<なぜこの設計を選んだか。代替案と却下理由>

## 用語定義

<このモジュール固有の言葉の意味>

## 注意点

<ハマりやすい点・暗黙のルール・将来変えたい負債>
```

## 品質チェックリスト

- [ ] 「なぜ」が書かれているか（「何を」だけになっていないか）
- [ ] 1年後に読んでも意味が通じるか（固有名詞・背景が自己完結しているか）
- [ ] コードを読めば分かる内容を書いていないか
- [ ] 設計の選択肢と却下理由が含まれているか
- [ ] 次に作る grasp-* Skill へのヒントになっているか
